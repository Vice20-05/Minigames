=====================================================================
        rpThread.txt - SWITCHING THE GAME LOOP TO YOUR OWN THREAD
                     (a thinking path, NOT the answer)
=====================================================================

This file does NOT give you the finished code. It gives you the
QUESTIONS to ask yourself, in the right order. Go step by step, run the
game after every step, and only open the hints at the bottom if you
are really stuck.

Files you will touch:  GamePanel.java  (most of the work)
                       KeyHandler.java (one small change)

Before you start: make a new git branch or commit your current work,
so you can always go back to the version that works.


---------------------------------------------------------------------
STEP 0 - UNDERSTAND WHAT YOU HAVE NOW
---------------------------------------------------------------------
Open GamePanel.java and find these 3 things:
  - where the Timer is CREATED   (constructor)
  - where the Timer is STARTED   (start())
  - what the Timer CALLS         (actionPerformed -> updateGame + repaint)

Ask yourself:
  ? Which thread runs updateGame() right now?
  ? Which thread runs paintComponent()?
  ? Why can they never collide right now?

If you can answer these 3, you understand the whole problem.
(Answers: Victor.txt section 5 + our chat about the EDT.)


---------------------------------------------------------------------
STEP 1 - WHO WILL BE THE "JOB" OF THE THREAD?
---------------------------------------------------------------------
A Thread needs a job to do. In Java that job is a Runnable,
which has ONE method:  run()

Think:
  ? Which class should have the run() method?
    (Hint: the class that already owns updateGame()...)
  ? What do you have to write in the class header so Java knows that
    class IS a Runnable?
  ? The class already "implements ActionListener" for the Timer.
    Do you still need that after the switch?

Then think about the Timer:
  ? Which lines become useless once the thread does the looping?
    Remove them only AFTER the thread works, not before.


---------------------------------------------------------------------
STEP 2 - THE LOOP ITSELF (in words)
---------------------------------------------------------------------
Inside run() you need a loop that keeps going while the game runs.
Write it on paper first, in plain words, like:

    while the game is running:
        remember the time now
        update the game
        ask Swing to repaint
        wait until it's time for the next frame

Think:
  ? What should the loop condition be? A boolean like "running" is a
    good idea. Who sets it to true? Who could set it to false?
  ? while(true) also works... but why is a boolean nicer?
    (think: pause menu, going back to the main menu later)


---------------------------------------------------------------------
STEP 3 - TIMING (the reason we're doing all this)
---------------------------------------------------------------------
We want 60 frames per second.
  ? How many NANOseconds is one frame?  (1 second = 1 000 000 000 ns)
  ? System.nanoTime() gives you "now". How do you get how long the
    update+repaint took?
  ? If one frame should take X ns and the work took Y ns, how long
    should you sleep?
  ? Thread.sleep() takes MILLIseconds. How do you convert?
  ? What happens if the work took LONGER than one frame?
    Can you sleep a negative time? What should you do then?
  ? Thread.sleep() can throw an exception. Which one? What do you have
    to write around it?

Tip: start SIMPLE. First make the loop work with a fixed sleep (like
the Timer did). Make it exact afterwards.


---------------------------------------------------------------------
STEP 4 - STARTING THE THREAD
---------------------------------------------------------------------
Look at start() in GamePanel.

Think:
  ? How do you create a Thread that does your Runnable's job?
    (Look at the Thread constructors - one of them takes a Runnable.)
  ? There are two methods that look right: thread.run() and
    thread.start(). Only ONE of them creates a new thread.
    Which one? What happens if you call the wrong one?
    (Try it! The window will freeze - good to see it once.)
  ? Should the thread be a field of the class or a local variable?
  ? Does requestFocusInWindow() still need to be there?


---------------------------------------------------------------------
STEP 5 - THE DANGEROUS PART: SHARED DATA
---------------------------------------------------------------------
Now 2 threads are working:
   game thread -> updateGame()       (CHANGES things)
   EDT         -> paintComponent()   (READS things)
                  keyPressed()       (CHANGES the key booleans)

Make a list on paper: which variables are touched by BOTH threads?
   (go through every field of GamePanel: road, player, traffic,
    spawner, score, ticks, gameOver... and the booleans in KeyHandler)

Then think about the worst one, the traffic list:
  ? What happens if the game thread does traffic.removeIf(...)
    while the EDT is in the middle of  for (TrafficCar car : traffic)?
  ? What about resetGame()? It replaces player, traffic, road with
    NEW objects. What if paint is halfway through drawing the old ones?

The tool you learned for this: synchronized.
  ? If only updateGame is synchronized, but painting is not -
    is it safe? Why not?
    (A lock only helps if EVERYBODY who touches the data uses it.)
  ? Both sides must lock on the SAME object. Which object?
    (Options: "this", or a special  private final Object lock.)
  ? What should NOT be inside the locked part?
    (Hint: what if you sleep while holding the lock? Who waits?)
  ? Keep the locked parts SHORT. Why?


---------------------------------------------------------------------
STEP 6 - THE KEYBOARD BOOLEANS
---------------------------------------------------------------------
KeyHandler's booleans are WRITTEN by the EDT and READ by the game
thread. They are simple true/false values, so a lock is overkill.

Think:
  ? Did you learn about the keyword  volatile ?  What problem does it
    solve? (search: "java volatile visibility")
  ? Which fields need it?  Does your "running" boolean need it too?


---------------------------------------------------------------------
STEP 7 - STOPPING
---------------------------------------------------------------------
  ? When the window closes, does your thread stop by itself?
    Right now GameWindow uses EXIT_ON_CLOSE, which ends the whole
    program, so it's OK for now.
  ? Later, with a main menu (DISPOSE_ON_CLOSE), the window closes but
    the program keeps running. Will your loop keep running in the
    background forever? How could the "running" boolean fix that?
  ? Bonus: look up  thread.setDaemon(true). What does it change?


---------------------------------------------------------------------
STEP 8 - CHECK THAT IT WORKS
---------------------------------------------------------------------
  [ ] The game runs and looks exactly like before
  [ ] Keys still work (click in the window if not!)
  [ ] Crash + R restart works 10 times in a row without an exception
  [ ] Play for 2-3 minutes with lots of traffic: no
      ConcurrentModificationException in the console
  [ ] Add an FPS counter to the HUD: count frames, and every time
      1 second passed, save the count and reset it. Is it close to 60?
  [ ] The Timer code is gone and there are no unused imports

Thread bugs are SNEAKY: they happen sometimes, not always. If you get
an exception only once in a while, that is almost always a missing
synchronized somewhere. Go back to your list from step 5.


---------------------------------------------------------------------
STEP 9 (OPTIONAL, LATER) - DELTA TIME
---------------------------------------------------------------------
Right now all numbers in GameConfig are "per frame" (ACCELERATION = 1.0
km/h PER FRAME). With delta time they become "per second".
  ? If one frame took 0.016 s, how much should the speed grow if
    acceleration is 60 km/h per second?
  ? Which places in the code use a "per frame" number?
    (PlayerCar, TrafficCar, Road, score, spawner countdown...)
Only do this after steps 1-8 work perfectly. It touches many files.


---------------------------------------------------------------------
COMMON MISTAKES (read when something is weird)
---------------------------------------------------------------------
- Calling run() instead of start()  -> window freezes, no new thread
- Sleeping INSIDE a synchronized block -> painting is late / laggy
- Locking on two DIFFERENT objects -> it looks safe but is not
- Forgetting the paint side of the lock -> random exceptions
- Forgetting to remove timer.start() -> the game runs TWICE as fast
  (two loops updating at the same time!)
- Negative sleep time -> IllegalArgumentException


=====================================================================
HINTS - ONLY READ IF YOU ARE STUCK ON A STEP FOR 15+ MINUTES
=====================================================================

Step 1 hint:
   The header becomes something like
       public class GamePanel extends JPanel implements ...
   and you must write a method with the exact signature
       public void run()

Step 3 hint:
   one frame = 1_000_000_000 / GameConfig.FPS   nanoseconds
   ns -> ms : divide by 1_000_000
   if the wait time is below 0, just don't sleep (or sleep 0)
   Thread.sleep throws InterruptedException -> try/catch

Step 4 hint:
   new Thread(this)   ... and then the method that starts it.

Step 5 hint:
   The idea, NOT the code:
       updateGame:      lock { all the changing }
       paintComponent:  super.paintComponent(...) , then lock { all the drawing }
       the loop:        sleep OUTSIDE the lock
   A method can be marked synchronized, OR you can use a
   synchronized ( someObject ) { ... } block. The block lets you keep
   the locked part smaller.

Step 6 hint:
   private volatile boolean upPressed;   (and the same for the others)

Good luck! When you're done, compare the "feel" with the Timer version.
